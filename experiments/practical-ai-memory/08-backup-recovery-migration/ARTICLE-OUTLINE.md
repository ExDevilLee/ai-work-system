## 结构

### 1. "直接复制"为什么不够

开篇用一个具体场景：Agent 发现记忆目录损坏，想从备份恢复。如果只是把备份文件复制回来，会发生什么？

引出六种故障模式（不逐一展开，只说"至少有六种情况会让直接复制变成错误决定"），然后提出核心设计原则。

### 2. 核心设计原则：权威源 + 验证清单 + 人工门禁

三个组成部分：

- **单一权威源**（source-manifest）：所有记录的 ID、路径、哈希、版本、范围和来源关系。它是唯一的事实源。
- **已验证备份清单**（backup-manifest）：从权威源确定性生成。记录哪些文件被备份、它们的存储哈希、哪些派生物被排除。
- **人工恢复门禁**：即使所有校验通过，恢复仍需人工批准。

用一句话概括：备份的价值不在"有一份副本"，而在"能证明这份副本和权威源一致，并且在出现分歧时知道该停下来"。

### 3. 六种故障场景：每种都是"直接复制"会犯的错

逐一介绍六个任务，用表格对比"直接复制会做什么" vs "带校验的恢复应该做什么"：

| 场景 | 直接复制的风险 | 正确行为 |
| --- | --- | --- |
| clean-restore | 可行，但绕过了人工批准 | 校验通过后仍需人工确认 |
| partial-backup | 用残缺包继续恢复，或补造缺失内容 | 识别缺失，停止恢复 |
| integrity-mismatch | 把篡改/损坏文件当成可信源 | 哈希不匹配，标记不可信 |
| target-divergence | 静默覆盖目标端的较新版本 | 停止，请求人工裁决 |
| derived-index | 把派生索引跨设备复制，当成事实源 | 索引由已验证源重建 |
| rollback-receipt | 把未通过验证的恢复标记为成功 | 回滚，通知人工 |

### 4. 三种条件：信息越多，越不需要人吗？

介绍实验设计：同一套源记录和故障场景，三种条件只改变可用信息量。

- source-only：只有源记录 + 目标盘点
- backup-inventory：加上备份文件清单和版本摘要（没有哈希校验结果）
- recovery-gated-bundle：加上完整备份清单、完整性报告和恢复门禁规则

**关键发现**：三个条件都允许满分。信息最少的 source-only 也能正确判断——但它的判断是"我无法确认，需要人工"，而不是"我确认了，可以继续"。人工门禁在任何条件下都不可省略。

### 5. 108 次正式尝试：保留失败，不写成全通过

简要描述实验规模和结果：

- 6 任务 × 3 条件 × 3 次 × 2 配置 = 108 次正式尝试
- 合计 99/108：2 个语义失败、6 个 deadline、1 个主线程中断
- 正式矩阵逐格完成机械评分与全量只读 Review
- 请求配置和 observed 字段分开记录，不把请求值写成实际身份

### 6. 正式矩阵发现的问题（透明记录）

- 无 receipt 时声称 receipt 校验失败，属于任务描述替代当前证据
- 无 backup hash 时借用 source 自哈希推进恢复资格，属于证据越界
- 夹具曾存在同名哈希字段语义不一致，r4 已统一并增加回归测试
- 失败样本保留，不修写成通过；评分由任务硬门禁、条件证据检查和只读 Review 共同完成

### 7. 四个关键设计决策

1. **完整性校验是门禁，不是报告**：哈希不匹配不是"警告"，而是阻断恢复的硬停止。
2. **冲突停机优于自动裁决**：当目标端有不同版本时，协议要求停止，不要求"选择更好的版本"。
3. **派生索引由源重建，不跨设备复制**：索引是衍生物，不是事实源；跨设备复制索引等于制造第二份真相。
4. **恢复后验证是必需步骤**：恢复完成不等于恢复成功；post-restore checksum 必须匹配。

### 9. 什么能落地，什么还需要更多证据

**能落地的**：

- 用 Markdown + JSON manifest 实现的备份清单和完整性检查
- 恢复门禁规则可以编码为可重复检查的合成任务
- 派生索引重建原则可以手动执行

**实验局限**：

- 合成场景不等于真实备份环境
- 两个请求配置不等于严格的单变量模型比较
- 108 次合成任务不等于真实恢复可靠性
- 未验证真实云存储、真实双向同步或性能
