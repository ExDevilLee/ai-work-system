# 为什么长期记忆需要一张“当前记忆地图”，而不应只藏在文件和索引里？

上一篇讨论了一个容易被忽略的差别：RAG 能把相关资料找回来，不等于系统已经知道此刻该执行什么动作。

这篇继续往前一步。即使资料都在文件夹里，索引也能找到它们，AI 和人仍会遇到同一个问题：一条规则已经被替代了吗？两条实验记录是不是冲突？某个结论只适用于 macOS，还是可以推广到全部平台？一次成功到底是稳定规则，还是待验证观察？

这些问题不是“再多读几篇文档”就一定能解决。它们需要一层很小、但明确的结构：**当前记忆地图**。

我的结论不是“所有长期记忆都要画成图”，也不是“状态投影一定比原始 Markdown 更准确”。更实用的结论是：

> 原始资料负责保留依据，索引负责定位资料，当前记忆地图负责声明哪些内容在什么范围内仍能指导行动。

![原始记录、当前记忆地图和当前行动之间的关系](images/06/current-memory-map.png)

## 1. 文件、索引和当前状态分别解决什么问题

一份原始记录可以保存决定、讨论、失败过程和复验原因。它适合回答“当时发生了什么”。

一个普通索引可以列出标题、路径、更新时间和摘要。它适合回答“去哪里找”。检索增强生成（RAG）的原始论文也把外部知识检索作为生成过程的一部分，解决的是模型如何接触相关知识[1]。

但“找到相关资料”与“恢复唯一当前动作”仍是两件事。假设同一主题下同时存在：

- 一条 14 天保留规则。
- 一条明确替代它的 30 天决定。
- 一次第三次重试成功的单次观察。

这三条都值得保留。可当前任务不能同时执行 14 天和 30 天，更不能因为一次观察就把重试次数改为三次。

因此，当前记忆地图不复制全部正文，而是为每条可行动信息保留最小字段：

| 字段 | 要回答的问题 | 没有它时容易发生什么 |
| --- | --- | --- |
| 状态 | 它是当前有效、已替代、冲突还是待验证？ | 历史记录继续驱动行动 |
| 范围 | 它适用于哪个平台、项目或流程？ | 局部结论被错误泛化 |
| 关系 | 它替代谁、和谁冲突、依赖什么？ | 新旧记录只按日期并排出现 |
| 来源 | 这项判断回到哪份原始资料？ | 投影变成无法复核的第二份事实库 |

## 2. “地图”不是装饰，而是行动边界

我把这层称为“地图”，不是因为它必须是节点连线图。它可以是 Markdown 表格、JSON 投影，也可以是带状态标签的界面。

关键不在视觉形式，而在它能否把下面五种边界写清楚：

1. `active`：在匹配范围内可以指导当前行动。
1. `superseded`：保留历史价值，但不能继续作为当前规则。
1. `conflict`：不得静默选边，需要补充受控复验。
1. `pending-validation`：可以保留观察，不能晋升为稳定规则。
1. `scoped`：只在明确的平台、项目或流程中有效。

这和事件溯源中“保存变化事件，再从事件重建当前状态”的思路有相通之处[2]。不过本篇的 POC 没有实现完整事件系统，也不试图处理并发写入；它只验证了一个更小的问题：当状态、范围和关系被显式表达时，当前行动是否仍然可追溯到原始来源。

## 3. 这次 POC 验证了什么

第六个 POC 使用同一份冻结 manifest 生成三种 Agent 工作区：

- `source-only`：只有合成 Markdown 原始记录。
- `flat-index`：增加标题、路径和中性摘要，但不泄露状态答案。
- `state-projection`：增加状态、范围、关系和来源指针，但不复制原始正文。

Agent 需要分别处理当前决定、已替代规则、未解决冲突、范围边界和待验证观察。每个任务检查事实状态、当前动作、边界、禁止结论和实际来源引用。

macOS 正式矩阵为 `5 个任务 x 3 个条件 x 3 次`，共 45 次，固定使用 `gpt-5.6-sol`、`medium` 和 Codex CLI `0.145.0`。三种条件均得到 `75/75`，每个任务/条件组合均为 `n=3`，没有协议异常、无依据断言或无关事实[3]。

这个结果很重要，因为它阻止了一个过强的叙述：**当前记忆地图没有在这组来源清晰、规模很小的合成任务中证明自己必然提高正确率。**

它证明的是另一件更克制的事：状态投影可以在不复制原始正文的情况下保留来源链路；而原始记录和普通索引在证据足够清楚时，同样可以恢复正确行动。

所以，是否维护这层地图，不应只看一次 benchmark 的分数，而应看项目是否已经反复出现以下治理成本：

- 同一规则的新旧版本经常并存。
- 平台或项目范围容易被遗漏。
- 冲突记录会被自动选成其中一个答案。
- 单次观察容易被写成稳定规则。
- 人工 Review 总要重新从长文中判断“现在到底以哪条为准”。

## 4. 人类也不需要为了“看图”而看图

POC 还准备了两种事实等价的人类界面：普通状态表和可视化地图。单名参与者在两种条件下均答对 5/5 题；地图条件耗时更长，并额外展开一次来源详情[4]。

这不是“表格比地图快”的证据。只有一名参与者、一轮任务和两套不同的合成场景包，不能推出任何人群层面的效率结论。

它反而提醒了一个很实用的设计原则：视觉化不是奖品。若一张图没有帮助人更快识别状态、范围和关系，它只是另一种需要学习的界面。地图应该服务于高风险变化、冲突和影响范围，而不是替代所有 Markdown 或表格。

## 5. 一个最小当前记忆地图怎么开始

不需要先建知识图谱，也不需要把所有资料都做成结构化节点。可以从少量高后果主题开始，每项只写清：

```text
主题：发布包保留期
状态：active
范围：当前项目的发布包
当前动作：保留 30 天后再清理
关系：supersedes -> 14 天历史规则
来源：records/decision-30-day.md
```

然后给系统加四条门槛：

1. 任何 `active` 项都必须有可读的原始来源。
1. 新记录不能默认替代旧记录，替代关系要显式写出。
1. `conflict` 和 `pending-validation` 默认阻止自动晋升或自动执行。
1. 范围不明时，系统宁可暂停并要求确认，也不要扩大适用范围。

这比“给 AI 一份更长的项目说明”更容易审阅。AI 不必把所有历史压缩成一段提示词，人也不必在每次任务前重新判断全部记录的有效性。

## 6. 当前地图仍然解决不了什么

当前记忆地图不是事实裁判，也不能替代检索、复验和批准：

- 它不能证明某条记录本身是真的。
- 它不能自动消解证据冲突。
- 它不能替代原始资料的上下文。
- 它不能保证所有模型都会遵守状态字段。
- 它不是 GraphRAG 或大规模关系推理系统的验证。

一些长期记忆系统会用分层存储、检索与调度来处理有限上下文和持续状态，例如 MemGPT 提出的虚拟上下文管理框架[5]。这些工作提供了有价值的设计背景，但并不等于本 POC 已验证其规模能力或通用效果。

对小型个人项目而言，更可靠的起点仍然是：先把“谁能指导当前行动”写清楚，再决定是否需要更复杂的存储、检索或图结构。

## 7. 平台与结论边界

本篇正式结果来自 macOS。Win11 将按第二系列的 Level 2 策略执行 15 次兼容性 Smoke，覆盖五个任务和三个 Agent 条件[6]。

在此之前，本文只能说“该机制已在 macOS 的冻结协议下实测”。即使 Win11 Smoke 通过，也只能补充兼容性结论，不能写成完整跨平台独立复现。文件系统、换行、编码、Shell、启动器和工具读取路径都可能改变实验过程，不能被隐藏在一句“跨平台可用”里。

## 9. 当前结论

长期记忆最容易失效的地方，不是文件丢了，而是历史、观察、冲突和当前规则混在一起以后，系统再也说不清“现在应该听谁的”。

当前记忆地图提供的不是更多资料，而是更短的行动边界：

- 原始资料负责解释。
- 索引负责定位。
- 当前地图负责声明状态、范围、关系和来源。
- Review 决定新证据能否改变当前状态。

下一篇将继续讨论一个更实际的边界：当这层当前状态已经形成后，怎样查看它覆盖了什么、哪些内容仍活跃、哪些项目需要治理，而不把记忆管理变成另一套难以维护的仪表盘。
