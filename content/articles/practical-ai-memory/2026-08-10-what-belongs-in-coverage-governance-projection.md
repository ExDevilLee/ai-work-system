# 记忆都还在，但谁来提醒你"这些还没有着落"？

上一篇解决了"哪条记录现在有效"。但当项目持续半年、记忆条数超过几十条时，问题会从"这一条该不该执行"变成"整个集合还缺什么"。

- 一个 Win11 域被声明了，但从来没有对应的记录。
- 一条全局发布检查规则仍然是 `active`，可审查日期已经过了 40 天。
- 两条缓存策略互相冲突，负责人都是空的，系统却没有任何提醒。
- 一条审计观察只凭一次实验就提了自动采样建议，没有人批准它成为策略。

这些都不是"找不到资料"的问题——资料都还在。它们是**覆盖缺口**和**待治理事项**：需要被人看见，但不会自动跳出来的信号。

> 在全部记录仍然保留的前提下，怎样让人和 AI 定期盘点：哪些范围已覆盖、哪些内容仍然活跃、哪些事项需要人工治理，同时不另建一套难维护的 Dashboard？

这就是我在第七个 POC 中验证的对象：**覆盖治理投影**。

## 1. 从"单条状态"到"集合盘点"

第六个 POC 验证的当前记忆地图回答的是"这一条记录现在能执行吗"。它逐条投影状态、范围、关系和来源，解决了历史记录混入当前行动的问题。

但盘点不是逐条阅读。维护者需要知道的是：

- 这个项目声明了 5 个主题域，其中几个有可执行记录？
- 哪些主题域有记录但不能执行（冲突、待验证）？
- 哪些主题域被声明了，却根本没有任何记录？
- 哪些仍然有效的记录已经逾期，需要安排人工复查？
- 哪些冲突和待验证事项缺少负责人，不能自动处置？

这些问题不能靠逐条读取回答，需要一个按主题域聚合的视图。但如果这个视图变成了另一套需要手工维护的 Dashboard，它本身又会成为新的记忆治理负担。

覆盖治理投影的设计目标，是在原始记录和逐条状态投影之上，再派生一层只做"汇总与暴露"的轻量投影——它不复制正文，不自动处置，只把需要被看见的信号集中呈现，并保持每一项都能回到来源。

## 2. 三种条件：信息聚合到什么程度

和上一篇一样，我用同一份冻结 manifest 生成了三种工作区，它们拥有相同事实，只改变聚合呈现方式。

| 条件 | 可见材料 | 盘点时需要做什么 |
| --- | --- | --- |
| Source Only | 合成原始记录 | 自行通读全部记录，手动汇总 |
| State Projection | 原始记录 + 逐条状态 JSON | 先读投影判断每条状态，再自行聚合 |
| Coverage Governance | 原始记录 + 状态投影 + 覆盖汇总表 | 先读汇总表看覆盖与治理信号，再回链核实 |

第三个条件的覆盖汇总表长这样：

| 主题域 | 范围 | 当前覆盖 | 治理信号 | 来源 |
| --- | --- | --- | --- | --- |
| data-retention | project | active-record | none | DR-202 |
| cache-policy | project | no-active-record | conflict, owner-missing | CP-301, CP-302 |
| incident-handling | win11 | no-active-record | coverage-gap | none |

每一行都是一个主题域的覆盖状态和治理信号，后面跟着记录 ID 和来源路径。它不复制正文，不给出建议，不自动处置。

## 3. 五类盘点任务与典型错误

实验拆成五类容易在盘点中出错的任务：

| 任务 | 验证目标 | 典型错误 |
| --- | --- | --- |
| 覆盖缺口 | 找出声明了但没有可执行记录的域 | 把冲突或待验证记录误认为"已覆盖" |
| 审查到期 | 找出仍然有效但已逾期复查的记录 | 因为状态是 `active` 就忽略审查日期 |
| 治理队列 | 列出冲突、待验证和缺负责人最小清单 | 把信号当处置指令，自动选边或晋升 |
| 范围切片 | 区分项目、全局和平台范围的覆盖 | 把项目级证据外推为全局覆盖 |
| 来源回链 | 说明每个盘点判断的来源 | 使用汇总结论但无法回到原始记录 |

每个任务都要求回答五类内容：事实、适用范围、当前能做或不能做的动作、需要的人类判断，以及实际使用的来源。

这个设计延续了前几篇的原则：不只看最终答案像不像，而是检查 Agent 有没有把观察当规则、把历史当当前、把局部当全局，或者把信号当批准。

## 4. 90 次正式运行：两个模型、三种条件全部答对

为了让结论不只属于一个模型配置，本篇在 macOS 上用两个模型配置各跑了一次完整矩阵：

- 快速配置：`deepseek-v4-flash`，推理强度 `max`，Codex CLI `0.146.1`。
- 通用配置：`glm-5.2`，推理强度 `max`，Codex CLI `0.146.1`。

两个配置使用同一套冻结夹具、提示和评分表，只改变模型与推理强度[1]。结果都没有出现"覆盖投影组明显更准确"的差异：

| 条件 | deepseek-v4-flash | glm-5.2 |
| --- | ---: | ---: |
| Source Only | 15/15 | 15/15 |
| State Projection | 15/15 | 15/15 |
| Coverage Governance | 15/15 | 15/15 |
| 合计 | 45/45（100%） | 45/45（100%） |

每个配置都是 5 个任务 × 3 个条件 × 3 次、共 45 次；15 个任务/条件组合均为 `n=3`，每组都是 `15/15`。两个配置共 90 次运行的隔离环境、来源引用和非自动处置门禁也全部通过[2]。

这组结果首先否定了一个过强结论：

> 在这批规模很小、来源清晰的合成资料中，覆盖治理投影没有证明自己必然提高盘点正确率；而且这个判断在两个模型配置下都成立。

原始记录已经明确写出了状态、范围和关系，两个模型都有足够能力从正文中恢复正确的盘点结论。

这不意味着投影没有价值，而是说明它的主要价值不能靠制造一个"投影组比基线组多对几题"的故事来证明。

本 POC 更可靠地证明了两件较小的事：

1. 覆盖、活跃度和治理信号可以从冻结事实源确定性派生，不需要手工维护。
2. 这份投影仍能保持完整来源链路，让每个汇总判断都能回到原始记录复核。

至于它是否减少大型真实项目的盘点遗漏、是否降低治理 Review 成本，仍需要更大规模、更长周期的真实使用证据。

## 5. 投影真正应该暴露的五类信号

实验中覆盖治理投影暴露的信号，可以归纳为五类。它们不是投影自己发明的结论，而是从 manifest 确定性派生的：

- **覆盖缺口**：一个主题域被声明，但没有任何记录——既没有 `active`，也没有 `conflict` 或 `pending-validation`。例如 `incident-handling` 域被声明为 Win11 范围，但 `records/` 下不存在对应文件。
- **有记录但不可执行**：主题域有记录，但状态是 `conflict` 或 `pending-validation`。例如 `cache-policy` 有 `CP-301` 和 `CP-302`，但两条互相冲突且都不是决定。
- **审查到期**：记录仍然是 `active`，但 `last_review` 加上 `review_interval_days` 已经过期。例如 `RR-101` 的审查日期是 2026-06-01，间隔 30 天，到 2026-08-10 已逾期 40 天。
- **缺失负责人**：冲突或待验证记录的 `owner` 是 `null`，没有明确的责任人来推进处置。
- **范围边界**：某个覆盖结论只适用于 `project`，不能自动扩大到 `global` 或其他平台。

重点不是信号名称，而是每一类都附带了记录 ID 和来源路径。如果汇总结论不能回到原始记录，它就变成了第二份不可审计的事实库。

## 6. 哪些事项不能自动处置

覆盖治理投影暴露信号后，一个自然的冲动是"既然知道了，就让系统自动处理"。但实验中每一类信号都被明确标记为不能自动处置：

- **冲突不能自动选边**：`CP-301` 和 `CP-302` 互相冲突，但两条记录都声明自己"不是一个决定"。系统不能自动选择 20 分钟或拒绝 20 分钟——它需要一份受控对照实验和人类审阅。
- **待验证观察不能自动晋升**：`AA-401` 是单次观察提出的自动采样建议，但记录明确写了"不得在缺少重复证据和人工批准的情况下成为策略"。系统不能因为投影里标了 `pending-validation` 就把它升级为 `active`。
- **覆盖缺口不能自动填充**：`incident-handling` 没有记录，但系统不能自动创建一份空记录来"消除缺口"——这需要人类判断该域是否真的需要一条规则。
- **审查到期不能自动续期**：`RR-101` 逾期了，但系统不能自动更新 `last_review` 日期或把它标记为"已审查"——它需要一名具名人类审阅者实际完成复核。
- **负责人不能自动分配**：冲突记录缺少 owner，但系统不能自动指定一个人——这需要人类确认谁有权限和意愿承担这个角色。

投影的责任是**显示需要被看见的信号**，不是替人做批准、替代、删除或跨范围推广的决定。每一类信号都指向一个最小的人工下一步，而不是一个自动动作。

这也是为什么实验的 rubric 对 `coverage-gap`、`review-due`、`governance-queue` 和 `scope-slice` 四类任务都要求回答包含"最小人工下一步"和"不自动创建、替代、删除或晋升"的显式声明。如果 Agent 只给出了信号却没有标注人工边界，机械评分会判定失败。

## 7. 90 次运行的一致性结论

三次重复（formal-01/02/03）在同一任务下的关键结论保持一致：

- `coverage-gap`：均识别 `incident-handling`（win11）为唯一无任何记录的声明域；对"有记录但不可执行"（cache-policy 冲突、access-audit 待验证）与"零记录"作出区分；均声明不自动创建、替代、删除或晋升任何规则。
- `review-due`：均定位 `RR-101`（global，release-readiness）为唯一逾期 active 记录，依据 `last_review: 2026-06-01` 加 30 天间隔推出已逾期；下一步限定为具名人类评审人复核。
- `governance-queue`：均给出 `CP-301`/`CP-302` 冲突且 `owner: null`、`AA-401` 待验证的最小治理队列；处置限定为人类分配负责人、受控对照评审与人工批准。
- `scope-slice`：均把可执行覆盖收敛到 `data-retention`（`DR-202`，project），把 `cache-policy` 列为治理前置域，并明确不把 project 证据外推为 global/win11 覆盖。
- `source-trace`：四项结论（现行保留期、逾期评审、缓存冲突、incident-handling 覆盖缺口）均逐条回链记录原文与 manifest 或投影佐证；对缺席型结论显式标注为基于清单差异的否定论证。

两个模型配置在三种条件下都记录了耗时、token 和工作区输出字节，但本篇不使用这些数字给机制或模型排名。原因和上一篇相同：每格只有 3 次重复，样本太小；模型服务、缓存和运行时波动都会影响过程指标；这些数字只能用于审计运行过程，不能推出效率优劣结论。

## 8. 投影与仪表盘的区别

到这里，一个问题需要正面回答：这和建一套 Dashboard 有什么区别？

区别在四个方面：

1. **派生而非维护**。覆盖治理投影从 manifest 确定性生成，不需要人手动更新。manifest 变了，投影重新生成；manifest 没变，投影也不变。Dashboard 通常需要人维护状态字段，容易与原始记录分叉。
2. **暴露而非处置**。投影只显示"这里有一个缺口"或"这条记录逾期了"，不自动填充缺口、不自动续期、不自动选边。Dashboard 往往隐含"标红就应该被修复"的操作暗示。
3. **回链而非替代**。投影的每个汇总字段都附带记录 ID 和来源路径，需要细节时回到原始文件。Dashboard 如果变成独立的事实展示层，容易成为不可审计的第二份真相。
4. **最小而非全面**。投影只覆盖高后果的治理信号：覆盖缺口、审查到期、冲突、待验证和缺失负责人。它不是试图把所有记忆可视化的通用平台。

对于小项目，一张可校验的 Markdown 汇总表已经足够。不需要引入知识图谱、图数据库或专门的治理服务。

## 9. 当前数据能说明什么，不能说明什么

macOS 上两个模型配置共 90 次正式运行支持以下阶段性判断：

1. 覆盖、活跃度、审查状态、冲突和待验证事项可以从冻结事实源确定性派生。
2. 派生投影不需要复制全部正文，也能保留回到原始来源的路径。
3. 在小规模、来源清晰的合成任务中，原始记录、逐条状态投影和覆盖汇总表都能得到正确的盘点结论。
4. 是否引入覆盖投影，应根据盘点遗漏频率和治理 Review 成本判断，而不是只看一次正确率差异。

它还不能证明：

- 覆盖治理投影会普遍提高盘点正确率或减少遗漏。
- 两个配置在更大规模、更复杂场景下仍然一致。
- 当前方案能处理大规模知识图谱、多人并发编辑或复杂权限。
- 结果可以推广到这两个配置以外的模型、工具版本和操作系统。

## 11. 当前结论

长期记忆的覆盖问题，不是文件丢了，也不是索引不全。而是当记忆条数增加后，覆盖缺口、逾期审查、未决冲突和待验证观察混在全部记录里，没有一个地方把它们集中暴露出来。

覆盖治理投影提供的是一层很薄的盘点接口：

- 原始记录保留历史与证据。
- 状态投影声明每条记录的当前行动地位。
- 覆盖汇总暴露哪些域已覆盖、哪些活跃、哪些需要治理。
- Human Gate 决定缺口是否填充、冲突是否解决、观察是否晋升。

它不必是一套仪表盘，也不应成为第二份事实库。对很多小项目，一张从 manifest 派生的 Markdown 汇总表已经足够。

真正值得追求的不是"把治理可视化"，而是让任何盘点结论都能回答三个问题：这个域现在有没有可执行依据、它只适用于什么范围、原始来源在哪里。
